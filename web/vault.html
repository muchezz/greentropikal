Copy it now. The part of the link after the # is the decryption key, and we do not keep a copy. If you lose the link, the secret cannot be recovered.

How it works

  1. You write the secret and choose how long it lives and how many times it can be opened.
  2. We encrypt it with a key generated for that one secret, then store only the ciphertext.
  3. You get a link. The key sits after the #, which browsers never send to a server.
  4. The recipient opens the link once. When the view limit or the expiry is reached, the record is deleted.

What this does, precisely

The claims below describe how Njira Vault is actually built. Nothing more is implied.

AES-256-GCM encryption Each secret gets its own random 256-bit key. The stored record holds only authenticated ciphertext.
The key is not in our database The key is returned to you in the link fragment and is never written to storage. The stored ciphertext alone cannot be decrypted.
Expiry is enforced by storage Every record carries a time-to-live and is removed when it lapses, whether or not anyone opens it.
One-time access is atomic The view counter increments and the record is deleted in a single storage operation, so a one-view secret cannot be read twice by concurrent requests.
No account, and no secret contents in our logs Njira Vault does not ask who you are, and secret contents and link fragments are never written to application logs.
What this is not This is not end-to-end encryption: the plaintext and the key both pass through our server while a secret is created and while it is read. Anyone holding the complete link can open the secret, and the link stays in browser history until it is cleared. Use it for temporary handoffs, not as long-term storage.
